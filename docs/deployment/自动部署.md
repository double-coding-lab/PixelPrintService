# GitHub Actions 自动部署

仓库提供 `.github/workflows/ci.yml`：提交和 PR 执行依赖安装、模板检查、预览环境准备、类型检查、测试和应用编译。只有当前仓库 `main` 的推送或手动执行，且配置了部署服务器时，才会自动发布。未配置部署变量的副本只运行检查。

## 部署过程

1. GitHub 托管 runner 编译应用，将提交编号与 `dist` 产物打包。
2. 通过独立 SSH 密钥传输，服务器固定主机指纹，不使用首次连接自动信任。
3. 服务器加部署锁，重新核对远端 `main`。排队期间已过期的提交直接跳过，不回退较新的发布。
4. 从对应提交导出干净源码，校验构建产物的提交编号、路径、类型和大小；本地私有配置不打包。
5. 运行依赖指纹与当前镜像一致时复用运行环境；依赖、准备脚本或实际构建配方变化时完整构建。两种方式都使用 CI 校验过的源码和编译产物。
6. 镜像模板检查通过后才切换应用。健康检查失败会用构建前保存的独立镜像标签恢复上一版；MySQL、Redis和文件卷保持原位。

部署使用独立密钥的 forced command，只接受 `deploy <40位提交编号>`。密钥不提供交互终端、端口转发或任意远程命令。服务器账号仍需操作 Docker 和发布目录的权限，管理者应按自己的机器权限策略设置部署账号。

## 服务器准备

先按[自主部署指南](部署与配置.md)完成一次部署。服务器需具备 Bash、Git、Python 3、Docker Compose、curl 和 `flock`。以下示例的代码目录为 `/opt/pixelprint`，可通过服务端固定入口的 `PIXELPRINT_DEPLOY_DIR` 指定其他路径。

安装部署入口到 checkout 以外的受控目录：

```bash
cd /opt/pixelprint
install -d -m 700 /usr/local/lib/pixelprint
install -m 700 scripts/deploy-server.sh /usr/local/lib/pixelprint/deploy-server.sh
install -m 700 scripts/deploy-ssh-command.sh /usr/local/sbin/pixelprint-deploy
```

在 `.runtime/deploy.env` 保存部署方的设置，权限设为 `600`。示例：

```bash
DEPLOY_COMPOSE_FILES='compose.yaml'
DEPLOY_DOCKERFILE='Dockerfile'
DEPLOY_HEALTH_URL='http://127.0.0.1:8080/health'
# 以下按部署网络需要填写，均不进入应用运行环境：
# DEPLOY_GIT_PROXY='http://127.0.0.1:7890'
# DEPLOY_BUILD_PROXY='http://host.docker.internal:7890'
# 自定义配方所需的额外普通文件，以冒号分隔；不要包含私有配置或凭据：
# DEPLOY_BUILD_FILES='.deployment-ca.crt'
```

外接数据库方案将 `DEPLOY_COMPOSE_FILES` 改为 `compose.external.yaml`；已有本机覆盖文件可用冒号追加。私有构建配方可以使用自己的 `DEPLOY_DOCKERFILE`，配方内容和声明的构建文件参与依赖指纹。

首次自动发布默认完整构建；后续成功发布记录指纹与实际镜像 ID。不要手工填写指纹来跳过准备检查。CI 不自动执行历史数据库的 ALTER 迁移，合并需要迁移的变更前，先按照[SQL 入口](../sql/README.md)安排备份与升级。

部署后生成 `.runtime/compose.release.yaml`，其中只覆盖 app 镜像；以后手动操作 Compose 时，也需将该文件放在覆盖列表末尾，否则可能切回旧的默认镜像。

## 专用 SSH 密钥与仓库设置

在可信的管理机器生成单独的部署密钥，私钥只保存到 GitHub Actions Secrets。不要复用日常管理员的 SSH 私钥：

```bash
ssh-keygen -t ed25519 -N '' -C pixelprint-github-actions -f pixelprint-deploy
```

将公钥添加到服务器部署账号的 `~/.ssh/authorized_keys`，在公钥行前添加限制：

```text
restrict,command="/usr/local/sbin/pixelprint-deploy" ssh-ed25519 <专用公钥内容>
```

在仓库 **Settings → Secrets and variables → Actions** 配置：

| 类型     | 名称                 | 值                                                              |
| -------- | -------------------- | --------------------------------------------------------------- |
| Variable | `DEPLOY_HOST`        | 服务器主机名或 IP；留空时不部署                                 |
| Variable | `DEPLOY_USER`        | 部署账号，默认 root；使用其他账号时需安排相应文件与 Docker 权限 |
| Variable | `DEPLOY_PORT`        | SSH 端口，可选，默认 22                                         |
| Secret   | `DEPLOY_SSH_KEY`     | 专用私钥完整内容                                                |
| Secret   | `DEPLOY_KNOWN_HOSTS` | 已核实指纹的 SSH known_hosts 记录，非标准端口需使用对应主机记录 |

主机公钥应通过已可信的连接或服务器控制台核对；不要只将未经核验的 `ssh-keyscan` 结果直接当作可信指纹。[GitHub Secrets 官方说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)介绍了页面和 CLI 配置方式。

## 查看结果与维护

在仓库 Actions 查看 **Check and deploy**。部署步骤输出最终提交编号，服务器 `.runtime/deployed-commit` 记录已通过健康检查的版本。支持 Actions 页面手动运行 `main`，同一提交重部署仍保留独立回滚镜像。

检查失败时不会启动部署；构建失败保留正在运行的旧应用；激活或健康检查失败尝试恢复旧镜像。健康检查验证的是服务就绪，真实 Figma 权限、用户模型服务、设计还原和交互效果仍需业务验收。

更新部署脚本后，由服务器管理者同步受控目录中的安装副本。发布前备份数据库、配置、密钥和文件；本流程不提供数据库回滚，也不会删除旧镜像或持久卷。旧发布暂存目录在结束时清理，镜像留存由部署者定期维护。

CI固定使用Ubuntu 24.04，与项目锁定的Playwright版本匹配；不要随意改为ubuntu-latest，较新的发行版可能尚未被该浏览器版本支持。生产镜像仍使用Dockerfile指定的Debian Bookworm。
