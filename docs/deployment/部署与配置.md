# 自主部署 PixelPrint

在线实例：[https://pp.lantao.work/](https://pp.lantao.work/)。使用者可直接阅读[使用指南](../使用指南.md)；本文面向部署者。

## 选择部署方式

| 方案                 | 启动文件                | 需要自己准备什么                                                |
| -------------------- | ----------------------- | --------------------------------------------------------------- |
| 一台服务器，全部本地 | `compose.yaml`          | 服务器、Docker、磁盘；Compose 提供 MySQL 和 Redis，文件存本地卷 |
| 使用已有数据库和缓存 | `compose.external.yaml` | 可达的 MySQL、Redis；文件仍可存本地                             |
| 使用对象存储         | 上述任一方案            | 提前创建的 S3 兼容桶、服务端凭据和浏览器可访问的素材域名        |

数据库、缓存、文件存储可以独立选择。例如 MySQL 和 Redis 用云服务、图片仍存本机，或只将文件改为对象存储。当前配置直接读取私有 JSON，修改后重启应用，无需额外配置中心。

## 资源与访问边界

可从 **4 核、8GiB 内存、100GB SSD** 的单机开始试用，初期将 `runtime.d2c.execution.concurrency` 设为 `1`；多人同时生成、编译和截图可从 **8 核、16GiB** 起步。这里是部署起点，实际容量取决于页面规模、并发和留存量，不是压测保证。模型通过外部接口调用时，不需要本地 GPU。

前端镜像构建允许 Node 使用最多 4GiB 堆，机器还需给 Docker、系统和数据库留内存。磁盘要容纳镜像、构建缓存、数据库、源码、图片与截图，应监控增长并定期备份。

公网入口开放 80/443；MySQL 和 Redis 仅供应用访问。默认 Compose 的 3306/6379 只绑定宿主机回环地址；8080 用于应用访问，配置反向代理后应由防火墙限制其公网入口。预览与应用共享机器账号和资源，保留 iframe sandbox、CSP 和资源校验，适用于受信团队；需要运行任意不可信代码时，应另行规划执行隔离。

## 单机部署

### 1. 准备软件和代码

服务器安装 Git、Docker Engine、Docker Compose 插件及 Node.js 24。宿主机 Node 用于生成配置；应用、Python、浏览器和编译工具由镜像安装。

```bash
git clone https://github.com/double-coding-lab/PixelPrintService.git
cd PixelPrintService
node scripts/setup.mjs --docker
```

首次初始化生成 `project.config.json`、本地管理员账号、随机密码和多组加密密钥。保存终端输出的密码；已存在的配置不会被覆盖。

### 2. 填写私有配置

编辑 `project.config.json`：

- `server.publicUrl`：浏览器实际访问地址，如 `https://pixelprint.example.com`；局域网试用可先填写 `http://服务器IP:8080`。
- `storage.publicUrl`：本地存储时填上述地址加 `/files`。
- `database.password`：换成自己的数据库密码。`--docker` 已将数据库主机设为 `mysql`、Redis 设为 `redis://redis:6379`。
- `runtime.d2c.execution.concurrency`：按机器资源设置，单机试用建议从 `1` 开始。
- `network.proxyUrl`：运行时能直接访问外部服务时保持空字符串。构建代理另见下文。

在仓库根目录创建 `.env`，使用与 `database.password` **完全相同**的密码：

```dotenv
PIXELPRINT_DB_PASSWORD=replace-with-your-own-long-password
```

包含 `$`、`#` 等字符时，按 Compose 的 `.env` 语法使用单引号保留原值；也可以使用足够长的随机字母数字密码。两处必须一致，否则应用无法连接 MySQL。该变量只影响新建数据库用户；已有 MySQL 数据卷更换密码需先在数据库中修改账号密码。

```bash
chmod 600 project.config.json .env
docker compose config --quiet
docker compose up --build -d
docker compose ps
docker compose logs --tail=100 app
```

镜像构建会执行 `npm run check:templates` 检查实际发布资源。核心模板 `pixelprint/` 必须完整；根目录 `skills/` 是可选的平台扩展，缺省时无需自行创建空目录。已有扩展仍随工作区冻结，符号链接及损坏资源会被拒绝。

首次构建下载依赖可能较久，可配置下述构建代理。应用启动会先执行 `db:init`，创建缺失表后启动服务；不会自动修改已有表结构。不要为升级执行 `docker compose down -v`，该选项会删除数据库与文件持久卷。

### 3. 设置用户和模型

使用初始化显示的账号密码登录，也可按下文启用 GitHub 或访客入口。每个人在应用的“模型凭据”填写自己的 **Base URL、模型名称、API Key**，并在“Figma 凭据”填写自己的 Token。模型接口需要支持工具调用，Base URL 使用兼容 OpenAI 的接口根地址，如 `https://model.example.com/v1`。

GitHub 和访客身份的生成任务必须绑定本人的模型凭据。平台 `runtime.modelConfigs` 保留模型预算、超时和可选默认连接；平台默认配置不替代外部身份的个人密钥。旧会话使用其已绑定修订，新设置主要对新会话生效。

容器中的 `localhost` 指向容器自身。外部模型、数据库和存储地址都必须从应用容器可达；Linux 宿主机服务如需通过 `host.docker.internal` 访问，需自行添加 `host-gateway` 映射，且宿主机服务须监听容器可达地址。

## 域名、HTTPS 和 GitHub 登录

### 域名与 HTTPS

1. 在 DNS 服务商处添加域名的 A 记录，指向服务器公网 IPv4。只有配置了相应 IPv6 入口时才添加 AAAA。
2. 在服务器配置 Nginx/Caddy 等反向代理，将域名请求转发到 `127.0.0.1:8080`。
3. 配置覆盖该域名的 TLS 证书与自动续期，将 `server.publicUrl`、本地 `storage.publicUrl` 改成 HTTPS 地址，重启应用。

**通配符证书只覆盖证书名称，不会自动创建 DNS 解析。** 即使已有 `*.example.com` 证书，`pixelprint.example.com` 仍需 DNS 记录或匹配的通配解析。

下面是 Nginx 示例；替换域名和证书路径，保留现有站点配置。使用 `nginx -t` 通过后再 reload：

```nginx
server {
    listen 80;
    server_name pixelprint.example.com;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl;
    server_name pixelprint.example.com;
    ssl_certificate /your/cert/fullchain.pem;
    ssl_certificate_key /your/cert/key.pem;
    client_max_body_size 30m;

    location = /auth/github/callback {
        access_log off;
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

### 登录方式

- **本地账号**：初始化自动生成，增加账号方法见[配置字段](configuration.md#增加账号)。
- **GitHub**：在 [GitHub OAuth Apps](https://github.com/settings/developers) 创建 OAuth App。Homepage 填自己的 `server.publicUrl`，Callback 填同一来源的 `/auth/github/callback`。在服务器私有配置填写 `auth.github.enabled=true`、`clientId`、`clientSecret` 后重启。客户端 ID 和密钥来自同一个 App；Secret 只在服务器保存，不发送到前端或提交到 Git。
- **访客**：设置 `auth.guest.enabled=true`，默认固定有效期 86400 秒。访客 Cookie 丢失、退出或过期后无法找回原身份；GitHub 登录不会自动接管访客数据。

GitHub 授权上下文保存在 Redis，有效期十分钟；域名、反向代理、Cookie、Redis和服务器到 GitHub 的网络都要正常。点击登录后完成一次真实授权回调，才算验证整条登录链路。更详细的身份边界见[配置说明](configuration.md#github-登录和访客)。

## 外接 MySQL、Redis 和对象存储

### MySQL

提前准备独立 MySQL 数据库与账号；推荐与默认镜像一致的 MySQL 8.4。修改以下字段，值为示例：

```json
"database": {
  "host": "mysql.example.internal",
  "port": 3306,
  "name": "pixelprint",
  "username": "pixelprint",
  "password": "replace-on-server"
}
```

账号需要初始化建表权限及运行所需读写权限；已有库需执行[增量 SQL](../sql/README.md)。服务端当前配置没有 MySQL TLS/客户端证书字段；强制证书认证的托管库需要先扩展连接适配或使用受信网络中的安全连接方案，不能仅填写主机名就保证兼容。

### Redis

```json
"redis": { "url": "redis://:password@redis.example.internal:6379/0" }
```

支持 ACL 用户名的示例为 `redis://username:password@host:6379/0`，TLS 连接使用 `rediss://`。连接串里的特殊字符需要 URL 编码。当前为单节点连接配置，没有 Redis Cluster/Sentinel 的拓扑字段；外部实例需与应用保持网络连通和所需命令权限。

### 文件存储：本地或 S3 兼容服务

默认 `storage.driver=local`，文件存应用持久卷，不需要另外购买文件服务。改为对象存储时：

```json
"storage": {
  "driver": "s3",
  "directory": ".data/files",
  "publicUrl": "https://assets.example.com",
  "bucket": "pixelprint",
  "region": "us-east-1",
  "endpoint": "https://s3.example.com",
  "accessKeyId": "replace-on-server",
  "secretAccessKey": "replace-on-server",
  "forcePathStyle": true
}
```

- 接口使用 AWS SDK 的 S3 `PutObject/GetObject`；AWS S3 可将 endpoint 留空。MinIO 等兼容服务通常使用路径风格；其他服务的 region、endpoint、寻址方式以供应商 S3 兼容文档为准。
- **OSS、COS 等不是填写一个上传 URL 就能接入。** 必须提供兼容 S3 的接口和凭据，并验证当前上传/读取操作；仓库没有原生 OSS/COS 专用 SDK 适配器。
- `endpoint` 是服务器上传与读取的 API 地址，`publicUrl` 是浏览器访问公开素材的根地址，可以分别使用内网 API 和公网 CDN。后者须能按相同对象键读取图片，应用不会自动创建桶、签名 URL 或 CDN 配置。
- 公开素材的读取权限由部署者配置；源码的大正文及全部新执行检查点、元数据和中间写正文以加密对象保存。`d2c-bodies/` 和 `d2c-checkpoint-bodies/` 前缀应保持私有，不要把整个桶无差别设为公开读取；仅为需要公开的素材前缀配置读取策略。
- 现有文件不会因改配置而自动搬迁。已有数据切换 driver、bucket 或根目录前，需规划对象迁移并验证历史文件回读。

应用单独启动，**使用独立文件而不是叠加默认 Compose**：

```bash
docker compose -f compose.external.yaml config --quiet
docker compose -f compose.external.yaml up --build -d
docker compose -f compose.external.yaml logs --tail=100 app
```

该文件不启动 MySQL/Redis，也不依赖本地同名容器。若只外接一个服务，可复制默认 Compose 到自己的部署文件，删去相应服务及 app 的对应 `depends_on`，同时修改私有连接配置。local 文件和执行临时目录仍需持久化。

## 下载代理与运行代理

**部署下载代理按需启用，默认不进入应用运行环境。** 如构建容器能访问宿主机上的 HTTP 代理：

```bash
export BUILD_HTTP_PROXY=http://host.docker.internal:7890
docker compose -f compose.yaml -f compose.build-proxy.yaml build app
docker compose up -d
```

外接数据库方案将上述第一项 `-f compose.yaml` 改成 `-f compose.external.yaml`，启动也使用外接服务文件。代理需要监听容器可达接口并限制访问来源。这里的 `127.0.0.1:7890` 会指向构建容器自身，不能直接代指宿主机代理。

覆盖文件仅设置 Docker 预定义的构建代理参数和构建主机映射，不添加运行时环境变量，也不修改 `network.proxyUrl`。参考 [Docker 构建代理说明](https://docs.docker.com/build/building/variables/#proxy-arguments)。此方式用于 Dockerfile 中的依赖下载；基础镜像拉取由 Docker daemon/BuildKit 配置自己的网络代理。不要将带密码的订阅 URL、代理密钥或个人模型 Key 写进镜像与仓库。

应用运行是否需要代理应另行判断：`network.proxyUrl` 用于 Figma 和 GitHub 的专用请求链路，直连可达就留空；个人模型与对象存储使用各自客户端，不会自动复用该字段。用户浏览器访问本站不经过这个服务器出站代理。

## 更新、备份与故障排查

- 更新前备份数据库、`project.config.json`、文件存储和需要保留的 Redis 状态；务必保留所有历史加密密钥。仅备份源码无法恢复用户数据。
- 拉取代码后先阅读 [SQL 升级入口](../sql/README.md)，执行所需迁移，再 `docker compose build app`、`docker compose up -d app`。外接服务方案在每条 Compose 命令加 `-f compose.external.yaml`。
- 容器内配置是私有挂载文件的副本。修改宿主机配置后可使用 `docker compose up -d --force-recreate app` 重新挂载；使用编辑器原子替换文件时，这比单纯 restart 更稳妥。
- `npm run pixelprint:update` 更新模板资源；已有工作区固定使用创建时副本，需要按工作区升级流程更新。

| 现象                       | 优先检查                                                                                   |
| -------------------------- | ------------------------------------------------------------------------------------------ |
| 域名无法访问               | DNS 是否指向本机、80/443 安全组、反向代理监听与证书；通配证书不等于通配 DNS                |
| IP 可访问、某个浏览器失败  | 对比无痕窗口，检查浏览器 DNS/代理缓存和扩展；先确认服务器响应，再针对浏览器处理            |
| 登录页有、本地密码登录失败 | Cookie 来源是否与 publicUrl 一致、是否经过 HTTPS、应用日志；跨来源提交会被拒绝             |
| GitHub 授权失败            | App ID/Secret、回调完整地址、Redis、服务器 GitHub 网络；查看安全错误提示，不公开回调授权码 |
| 数据库连接失败             | 容器可达地址、密码与已有库账号是否一致、账号权限、迁移状态                                 |
| 下载依赖超时               | 构建网络及构建代理；镜像拉取与容器内下载分别检查                                           |
| 预览/截图失败              | app 日志、源码诊断、图片依赖、Chromium 安装与机器内存                                      |

发布后实际验证：登录 → 填个人模型/Figma 凭据 → 生成一个页面 → 预览和交互 → 保存与下载 → 重启后回读。日志检查使用 `docker compose logs --tail=100 app`；不要在公共 issue 粘贴私有配置或原始密钥。

## 本地开发

```bash
npm ci
npm run setup
docker compose up -d mysql redis
npm run db:init
npm run prepare:images
npm run prepare:preview
npm run dev
```

本地配置使用 `127.0.0.1` 的数据库和 Redis。数据库密码仍需与 Compose 的 `.env` 保持一致；模型可在应用中按人设置。Linux 浏览器依赖安装面向 Debian/Ubuntu，安装系统库需要 root 或 sudo。

```bash
npm run typecheck
npm test
npm run build
npm start
```

### 执行状态文件存储与旧数据兼容

- 检查点使用 `runtime.d2c.checkpointStorage` 的独立密钥及已就绪引用列；新实例沿初始化配置创建，新版本读取旧数据库正文和旧单文件引用。配置未就绪时拒绝新增执行状态正文，避免回退数据库。
- 新执行状态正文全部文件化。`runtime.d2c.limits.uploadBytes` 控制单文件上传上限，超过后自动分块；当前单条执行状态正文上限128MiB，最多256块，数据库只保存小引用。旧 `mode` 和 `thresholdBytes` 保留配置解析兼容。
- 升级先备份数据库、文件和历史密钥。历史数据通过兼容读取继续使用，批量迁移由显式 `checkpoint:migrate` 完成；旧程序回滚前须先核对格式兼容性，显式恢复所需BLOB时还要核定数据库报文限制。升级程序不自动迁移历史、不清理孤立上传文件。
