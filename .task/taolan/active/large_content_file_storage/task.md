# 大正文迁移到文件存储

## 当前状态
2026-11-21：第一阶段代码已双仓接入并完成离线回归，包含平台适配、三模式灰度、兼容旧正文、新建库结构、业务冻结与读取、迁移和回填工具。默认关闭，目标库仍沿用原存储。

本轮未执行真实DDL/DML、对象上传、历史迁移、清理或部署；实际容量和性能验收仍需部署方完成。本次改动保留在codex/content-storage-phase1，实现与测试已提交，知识库和部署说明随本次文档提交保存；本轮仅本地提交。

## 目标与范围
- 数据库保留权限、状态、修订、顺序、关联及大小/摘要/对象定位等元数据，大正文按用途迁出。
- 不以LONGTEXT类型作为唯一迁移依据；JSON/LONGBLOB中的大正文也需盘点，小配置和需事务查询的数据继续留库。
- 部署升级兼容线上旧数据、旧会话/版本及执行进度；项目复用核心存储协议，以新结构为主，但不得默认已有部署数据可丢弃。
- 目标是降低数据库大记录读取、排序、传输和备份压力；文件化不承诺自动解决所有MySQL或Node.js内存故障。

## 本轮实施边界
- 第一阶段代码交付：统一正文存储协议及适配、当前文件/Figma缓存/版本/作品/预览正文的读写改造、灰度控制、离线回归及迁移工具。实际对象存储接通必须先通过保密性与限额检查。
- 第一阶段保留现有数据库排序优化；不修改Agent检查点和中间写入的存储格式，不启动历史正文清理或对象自动删除。
- 第二阶段仅出时间线/检查点/中间写入评估，实施另行排期。项目未确认无历史用户前采用保守升级路径，不能重建或清空数据库。
- 小正文可按可配置阈值保留数据库，大正文外置；阈值由离线性能数据确定，不默认每次小写入都访问对象存储。

## 备注
- 新正文使用不可变对象；禁止原地覆盖旧对象破坏已冻结版本或检查点。
- 数据库与文件存储没有跨系统原子事务：先写并校验文件，再短事务提交引用；事务失败的孤立对象由延迟回收处理。
- 按引用/版本保留策略回收，不能仅以文件年龄删除历史仍引用的正文。
- 2026-11-21只做了最小源码核验和计划更新；未查询线上数据库、试跑迁移或修改业务代码。线上容量/内存排名未知，不把代码推断当作运行测量。
- 已核实4f73ee7将大字段查询改为先分页标识再读取正文；本任务在此基础上验证正文存储优化，不重复把排序修复当作文件外置能力。
- 当前D2cFile将content用于文本、objectLocator用于二进制；files/service.ts以content是否为空及objectLocator是否存在判断可编辑/可读文本。应设计独立且带版本的文本正文引用，不能只把content设NULL或直接挪用二进制定位而破坏文本接口。
- 灰度顺序须明确：旧数据兼容读取→写入并保留库内正文的验证期→确认无旧实例写入后再启用仅外置正文。验证期旧实例修改正文时，新的引用必须与当前摘要/修订绑定，过期引用不得覆盖新正文。
- 回滚分两类：新应用关闭外置写入不等于旧应用可读取已外置数据；回滚旧程序前须保留或回填其所需的库内正文，并校验完整性。
- 源码、缓存和内部执行资料走私有对象通道；若底层文件服务不能提供所需访问隔离，需先设计服务端加密、密钥轮换/恢复与受控读取。不能直接上传明文到公开图片/CDN通道，也不能把文件定位暴露给无权用户。
- 历史迁移工具先支持dry-run和可恢复批次；真实数据迁移、旧正文清理和垃圾回收由部署方在备份及观察期后执行。
- 下一步：部署方按实施说明采集真实容量/性能基线、审核DDL及灰度验证；任务保持active，代码交付与真实迁移分开验收。
